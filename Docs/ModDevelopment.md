# 模组开发规范

返回 [贡献指南](../CONTRIBUTING.md)。按本次任务阅读相关章节。

## 模组日期与文档范围

- 模组不维护独立语义版本。使用 `releaseDate`，格式为 `YYYY-MM-DD`；同日修订由自有载荷 SHA256 区分。安装状态同时核对日期、载荷指纹和受管理文件完整性。
- 项目的 `ModReleaseDate` 与定义日期一致；.NET 和 BepInEx 要求的数字元数据由日期映射为年、月、日，不另设版本序列。发布时重编插件并同步定义及哈希。
- 新安装清单采用日期格式；旧数字版本仅为读取、更新和卸载已有安装保留兼容，不在新界面或新清单中展示为模组版本。
- 根目录 README 仅描述平台能力和使用方法，不列特定游戏。Mods/README 仅保留功能汇总及游戏说明链接。任何游戏专属名称、AppID、类型和命令实例只能出现在 Mods 内的文档中。
- 游戏 README 是长期使用与维护说明，可记录当前功能、构建入口、兼容边界和验证要求；不得追加逐轮工作日志、历史验收记录或临时证据。源代码、定义和测试中的必要游戏标识不受文档范围规则限制。

- 启动器维持单实例。同版或新版已运行时激活已有窗口；发现可识别的旧版时提示“是／否”：是则关闭该旧版并启动当前版本，否则激活旧版并退出新进程。只有用户在提示中选择“是”才可终止该旧版进程；关闭失败须提示，不启动第二实例。


## 模组安装、更新与删除

- 专用模组及其功能定义随启动器内嵌。更新专用模组意味着更新启动器；普通构建不在线拉取可变的最新专用代码。
- 首次安装从固定官方 HTTPS 地址下载通用组件，按平台／架构／运行时／版本缓存到 `%LocalAppData%\KairoGamesToolbox\Mods/Runtime`。下载有大小上限、超时与 SHA256 验证，缓存每次复用前验证；失败不安装。
- BepInEx、.NET 和互操作支持是共享组件，不等于所有游戏都能共用一个架构包。新游戏必须单独确认 Mono／IL2CPP、x86／x64、Unity 与运行组件兼容性。
- 安装前验证游戏 `GameAssembly.dll` 和 `global-metadata.dat` 指纹；不匹配不写入。共享包与专用文件都有清单和指纹。
- ZIP 路径必须防穿越、重复、Windows 保留名、重解析点；限制条目数和解压体积；不能允许 payload 覆盖原商业游戏文件。
- 安装／更新使用暂存和备份，失败回退。临时组合包不重复压缩，边复制边计算 SHA256；更新仅解压、备份及替换实际变化文件，仍校验全部载荷和受管理文件，不以性能为由跳过完整性或回滚保护。只能替换指纹匹配的已管理旧文件或相同的新文件，未知修改拒绝覆盖。
- 删除依据安装清单和指纹，仅处理已管理文件；事务失败恢复。不得递归删除整个游戏目录、存档、未知插件或全部 BepInEx 文件夹。
- 删除 Mod 恢复未修改游戏的启动方式，但**不回滚存档数值**；界面与文档不得混淆两者。生成的配置／日志／interop 可保留。
- 进入详情时异步检查安装记录版本、内置专用文件指纹及已管理文件完整性；已是最新且完整时禁用更新按钮。安装与更新共用按钮，卸载为单独按钮。安装与更新不得通过通用游戏进程名判断目标游戏是否运行；完成指纹与事务预检查后直接尝试安装，失败显示实际原因，文件被占用时提示关闭目标游戏重试，不自动结束进程。卸载前弹窗提醒关闭目标游戏，确认后直接尝试卸载；不得因发现任意同名游戏进程而阻止，失败报告实际原因。


## 模组控制与稳定性

- 功能 ID、四语言文字和日志规则来自游戏定义。所有现有及后续游戏的倍率固定为 0／1／50，不允许其他档位；0 倍标注“不消耗”，含义是返还实际消费、净变化为零，不能绕过购买条件，也不等于关闭开关。协议、界面、插件、定义和测试必须同步。
- 新游戏接入按需求确认身份、静态签名与资源语义；复用匹配游戏版本的互操作程序集和已有证据，缺失证据时才增加定向探索或只读观察。过程证据留在任务或忽略目录；只将必要的当前技术约束更新到模组说明或定义中。中间构建与交付验证按 [开发验证表](DevelopmentGuide.md#按变更选择验证) 选择，不固定探索规模或用户介入轮次。
- 开发加载探针允许 `features=[]`、`development=true`，只连接状态与展示原始日志，并明确提示没有修改项；不能把通信成功等同于游戏钩子成功。插件检测从游戏定义读取路径，禁止在通用逻辑写死某个 DLL。完全不接触游戏对象的探针可以在后台响应，实际修改仍必须交给游戏主线程。
- 协议和结构共享源码；版本 2 的请求／响应严格验证协议、AppID、目录、游戏 Session、功能集合与倍率。命名管道仅限当前 Windows 用户。
- 手动刷新不能因自动检查占用锁而静默丢弃：立即显示忙碌状态，等待串行执行，整个手动检查最长 6 秒，失败须有可见提示；离页取消旧请求。
- 自动连接检查前后均 15 秒，只在模组控制页可见且已检测到 Mod 时通信。离页、切目录或切语言取消旧请求，迟到响应不能修改新状态。
- 开关状态来自游戏确认；断线保留显示并禁用交互。只在启动器进程内记忆，按游戏目录隔离；游戏重启或重新连接时恢复，新启动器进程默认全部关闭。
- 连接后可以立即选择开关，不能要求用户先进入存档或使用热键；模组内部通过读取原生 AppData 单例等待游戏对象就绪，不得要求所有静态门面／可选资源类的初始化标志同时成立，禁止在插件 Load 中强行运行游戏静态构造函数。
- 游戏修改在正确线程与真实入口执行；实际扣除后才补回。倍率不得放大正常收入，必须防溢出、重复补回和嵌套调用。
- Harmony void 目标不能绑定 `__result`；long 返回值使用专门 postfix。原游戏异常必须保留，失败时清理部分钩子，不能无限重试初始化。
- 所有 Mod 默认关闭所有功能，只接受启动器控制，无独立热键。关闭开关影响之后的事件，不恢复已经保存的数值。
- 运行日志提供清空和自动刷新开关；清空仅清理显示并推进读取游标，不删除游戏磁盘日志。游戏 Session 改变、文件截断或重写时清除旧内容；即使重写后长度超过旧游标也应检测。暂停刷新后可恢复增量读取。
- 日志支持跨行选择、复制及一键复制全部当前保留内容；采用有界队列与增量读取；资源最终结果翻译，未知诊断保留。开发模式不翻译，错误不能被成功模板掩盖。限制内存列表，不每次刷新重建开关造成闪烁。


## 开发完成时收尾

- 成品交付前，按当前构建和调用关系移除废弃探针、无调用代码、旧测试入口、一次性工具及失效文档引用。需要历史实现时从 Git 历史查阅，不建立归档目录，也不以注释或排除编译代替清理。
- 从探针转为正式功能时，同步文件、类、命名空间、项目和脚本名称，使名称表达当前职责；连同项目引用、内嵌资源及签名检查一起更新。不能把文件改名后仍保留误导性的内部类名。
- 已发布的程序集名、插件 GUID、安装路径及协议标识属于兼容约定，不按美观直接更换；需要迁移时同时实现旧安装升级与验证。具体兼容标识仅记录在对应游戏说明中。
- “更新 Mod”默认包括修改源码、重编新 DLL、同步日期及载荷 SHA256，并将新 DLL 内嵌到启动器。不得只更新界面、定义或源码而继续交付旧 DLL。缺少依赖时明确报告阻塞，不声称模组更新完成。游戏内验证由用户完成时，不自动部署、启动或操作游戏。
- 完成时检查受影响源码、脚本、测试、文档的引用闭合，并运行对应验证；不新增清理报告或阶段验收文档。发布成功后按 [构建规范](Release.md) 清理编译缓存，普通开发测试保留可复用缓存。
